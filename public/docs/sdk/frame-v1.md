# Blaze frame bridge v1

This describes the Frame v1 behavior implemented by the Blaze SDK. A game integration still needs its owner to implement and review the frame side, consent, and any permitted capture surface. Actual Forever integration and end-to-end acceptance remain unverified.

The trusted parent loads `https://blaze-bensigo.netlify.app/sdk.js`, configures `Blaze.init` with its own approved game key, endpoint and analytics consent, and owns the network connection. Register that parent page's exact origin in the game's allowed origins: it sends `/api/collect`, not the opaque iframe. Do not register `null` or use a wildcard. The embedded game remains in its existing sandbox with its opaque origin and existing restrictions. The worker may load only the separately reviewed frame URLs described below; the host must retain its existing sandbox and frame restrictions.

After the specific game iframe has loaded, the trusted parent creates a `MessageChannel`, generates a fresh unguessable base64url nonce of 24–128 characters, calls `Blaze.attachFrame({frame, port: channel.port1, nonce, canvas})`, and transfers `channel.port2` directly to that iframe's `contentWindow`. Since its origin is opaque, a direct `postMessage` to that *specific window* may require `'*'`; the receiver must verify `event.source === parent`, reject unexpected handshakes, and retain the transferred port privately. Never broadcast, expose the port or nonce, or reuse it between games, frames, sessions or navigations. Bind only one configured game to the bridge. The parent must call the returned `close()` when changing game, unmounting, or withdrawing access; iframe load/navigation and page exit also close the bridge. Establish a fresh channel after each load.

The handshake envelope is owned by the host integration; the port payload below is the complete v1 SDK contract. Each message on the private port is a plain object with `v: 1`, the negotiated `nonce`, and a strictly increasing safe integer `seq` beginning at 1. Unknown fields, versions, stale/non-increasing sequences, or malformed payloads are ignored. The bridge processes at most 20 valid messages per one-second burst; excess messages are dropped. Lifecycle events and activity require analytics consent. The explicitly activated local owner preview described below is the only compositing path available without analytics consent. The SDK emits no human events in the existing marked Blaze worker session.

The parent's automatic `loaded` event describes its document load, not completion of the embedded game's assets or engine startup. Frame v1 does not accept `visit`, `loaded`, `ui_click`, `player_action` or `milestone` messages. Do not label parent document readiness as measured iframe/game readiness.

- Lifecycle: `{v:1,nonce,seq,type:'event',name,properties?}`. Names: `first_action`, `round_start`, `round_complete`, `retry`, `progression`, `error`, `exit`. `round_complete` may have `{result:'win'|'loss'|'draw'|'complete'}`; `progression` may have `{level: integer}` from 0 to 1000; `error` may have `{code:'asset_failed'|'network_failed'|'runtime_failed'}`. Other names accept no properties. Do not send names, chat, account/opponent details, hidden game state, arbitrary text, or URLs.
- Input activity: `{v:1,nonce,seq,type:'activity',at: Date.now()}`. Send at most once per second only from a reviewed frame listener handling a real `event.isTrusted === true` input. The parent checks freshness and rate; it cannot independently prove a child event was trusted. Do not transmit or accept a `human`, `agent`, or `isTrusted` flag as proof of identity.
- Pointer sample: `{v:1,nonce,seq,type:'pointer',x,y,screen}`. `x` and `y` are finite normalized coordinates from 0 to 1 on the reviewed gameplay surface; `screen` is a stable game-defined identifier of 1–40 ASCII letters, digits, underscores or hyphens. Reviewed child code sends only from real `event.isTrusted === true` pointer input and excludes private regions; the parent cannot independently verify that claim. No arbitrary text, URLs or player details. With analytics consent and the parent in the foreground, the SDK forwards at most one sample per second as `pointer` with `{x,y,surface:'game',screen}`. Native parent pointer samples use `{surface:'viewport',screen:'viewport'}`; neither kind is a semantic replay. No pointer, lifecycle, or activity message is emitted while the owner preview is active.
- Optional gameplay image: `{v:1,nonce,seq,type:'frame',bitmap,at}` with a transferred `ImageBitmap` at most 1920×1080 and `at: Date.now()` recorded when that bitmap was generated. The host supplies an explicit, attached gameplay-only parent canvas as `canvas`; the SDK draws at most 5 fps during an activated owner preview, or while separately consented capture is recording and the capture's server-approved selector resolved to that exact canvas. It closes every received bitmap and never takes a DOM snapshot. Existing v1 preview/recording messages without `at` remain accepted, but **starting each capture segment requires a fresh timestamped bitmap**. Player capture still requires reviewed masks, consent, sampling, quotas, and up to four 30-second segments. A DOM-only game is unsupported for this path unless the owner implements and reviews a gameplay-only compositing surface; never include chat, names, UI outside the game, or hidden state.

When `Blaze.startCapture({consent:true})` begins, the parent observes the `blaze:capturestatus` event with status `starting` and must start feeding timestamped frames immediately, before awaiting the `startCapture` promise. After the server grants capture and its unique selector resolves to the same attached canvas, Blaze clears that canvas and waits up to three seconds for a valid, current bitmap generated after the gate opened. A previous preview or previous segment cannot satisfy this gate. The recorder starts only after that bitmap is drawn; `recordedAt` is its actual recorder start time. Each later segment repeats the gate. A missing fresh frame returns `failed` with reason `frame_timeout` and uploads nothing. Withdrawal, navigation or bridge teardown aborts the wait; an ordinary canvas not bound to a frame bridge retains its existing capture behavior. This timestamp is provided by reviewed frame code; it is not a bot-authentication mechanism.

### Local owner preview

The owner may inspect the supplied game-only canvas before enabling analytics or capture. The parent may supply `previewMasks` when attaching the bridge: an array of up to eight normalized `{x,y,width,height}` rectangles, which are blacked out in the preview. These are only local preview masks; the server's reviewed capture masks still apply independently. The supplied canvas and source bitmap must each be at most 1920×1080.

Call `bridge.startPreview(event)` **synchronously inside an explicit owner review button's real trusted click handler**. Pass the browser `Event` itself (in React, `event.nativeEvent`); a plain object, synthetic click, expired event, or reused event is rejected. Where the browser exposes `navigator.userActivation`, active user interaction is also required. The method returns `{status:'previewing', expiresAt}` and opens the same private-port bitmap path for at most 30 seconds. The preview is local and in memory: it does not grant analytics consent, send telemetry, start recording, persist frames, or upload data. It cannot run in a marked worker session or during capture. Call `bridge.stopPreview()` to stop early; timeout, page hiding, iframe navigation, bridge close, or consent withdrawal also stop it and clear the canvas. Starting capture ends any preview. Owner preview does not authorize or configure player capture.

Example parent setup (after iframe load; `frame` and optional reviewed `canvas` are owner-controlled):

```js
const bytes = crypto.getRandomValues(new Uint8Array(24));
const nonce = btoa(String.fromCharCode(...bytes)).replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
const channel = new MessageChannel();
const bridge = Blaze.attachFrame({ frame, port: channel.port1, nonce, canvas });
frame.contentWindow.postMessage({ type: 'blaze:port', v: 1, nonce }, '*', [channel.port2]);
reviewButton.addEventListener('click', (event) => bridge.startPreview(event));
// On game change or unmount: bridge.close();
```

A game-frame `activity` message is not an authentication or bot-detection mechanism. Blaze's local worker marker suppresses its own human SDK reporting, but a browser flag alone cannot prove synthetic traffic to Forever or exclude it from Forever's own counters. Use the server-to-server handshake below for that purpose.

The worker gameplay API is `window.BlazeGameAdapter` (or legacy `window.gameMarketingAdapter`): `getState()`, `actions` (`{id,label}` array), and `act(id)`. State and actions must be reviewed and limited to public gameplay without hidden cards, other players' data, navigation, messaging, purchases, or credentials. A terminal phase can return an empty action list. The parent adapter owns its game-specific private port and must not expose it to the worker; the worker calls only the reviewed parent adapter. Never enable blanket subframe access.


## Synthetic recording handshake

This handshake is implemented in Blaze; each game server still requires its own integration and end-to-end acceptance. A worker-authenticated recording claim mints a random 256-bit capability, stored only as a hash and scoped to workspace, Blaze game ID, recording, game origin, and an expiration no later than five minutes. The active recording lease is checked at mint and on every verification. Clip claims and the controlled fixture receive none. The worker sends the opaque value only as `x-blaze-synthetic-capability` on the first main-document GET to the exact configured HTTPS game URL. It removes the header from redirects and every other request. It is never placed in a query, browser script, SDK configuration, frame message, or general context headers.

The game server reads the header on that initial request. It must use its own server-configured Blaze game ID and canonical game origin, create its own opaque guest session ID, and send this server-to-server request to Blaze over HTTPS. Do not trust game ID, origin, guest ID, or a synthetic flag supplied by the browser. Do not log or return the capability to the browser.

```http
POST /api/integrations/synthetic/verify HTTP/1.1
Host: blaze-bensigo.netlify.app
Content-Type: application/json

{"capability":"<opaque-43-character-base64url>","gameId":"<server-configured-blaze-game-id>","origin":"https://game.example","guestSessionId":"<server-generated-guest-session-id>"}
```

The response is `200 {"synthetic":true}` only for a valid capability bound to that same guest session. First success binds it atomically; retries for that session are idempotent. Different sessions, game IDs, origins, expired capabilities, or inactive leases receive `403 {"synthetic":false}`. Malformed requests receive 400; rate-limited requests receive 429. Treat timeouts, unavailable verification, and every non-200 response as unverified and do not classify the guest as synthetic. A capability is not an SDK key, and no public browser flag authenticates it. Each field is a string; game and guest IDs use 1–200 ASCII letters, digits, underscores, or hyphens. The verification request is limited to 2 KiB and a global rate ceiling. The response discloses no workspace, recording, account, or player data.

After successful verification, the game server should persist the synthetic classification on its own guest session and apply it to its own counters and events. Verification happens while the lease is active; the verified classification belongs to that session thereafter. Keep guest-session binding server-controlled and unique. The target server must not verify as synthetic by trusting the browser marker.

## Reviewed worker frame URLs

`networkPolicy.frameUrls` is optional and contains at most two canonical, exact HTTPS URLs without wildcards, query, fragment, credentials, or encoded slash/dot/backslash. Each must share the configured main game origin; save-time and run-time DNS checks require public IPv4. For example, `{"resourceOrigins":[],"webSocketOrigins":[],"frameUrls":["https://game.example/whot.html"]}`. This is a per-game owner-reviewed allowlist, not an origin-wide frame grant. Main-document navigations must remain on the game origin; cross-origin redirects are denied. Frame redirects are denied, including same-origin redirects. Unknown/private URLs and nested frame navigations are denied; popups and workers remain denied. The worker adds a restrictive sandbox CSP to permitted frame documents, preventing same-origin parent access and network connections; existing host sandbox attributes remain in force. Additional resource origins and WSS require their own prior explicit policy and are not granted by `frameUrls`. A reviewed frame cannot access the capability.

These controls have controlled-fixture tests only. Real-game integration, its full guest flows and counters, physical-device capture behavior and audience acceptance require separate end-to-end verification.

The public browser entry point and complete analytics rules are in the [quickstart](https://blaze-bensigo.netlify.app/docs/sdk/quickstart.md) and [SDK v1 reference](https://blaze-bensigo.netlify.app/docs/sdk/v1.md). Synthetic worker records and controlled fixtures are test evidence, not audience activity.
