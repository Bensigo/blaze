# Blaze browser SDK reference v1

Start with the [quickstart](./quickstart.md). The SDK is a classic browser script, exposed as `window.Blaze`. `window.GameMarketing` is a deprecated alias. Load it from the Blaze deployment at `/sdk.js`; `Blaze.init({endpoint, sdkKey, consent?})` requires an HTTP(S) app origin and the game's public SDK key. The endpoint is reduced to its origin. Register the game's exact origin in Blaze. The game ID is for dashboard and API identification, not an `init` parameter. The key is public and identifies the game; never embed secret credentials. The game page must implement its own affirmative consent choice.

## Analytics API

- `Blaze.setConsent(true)` starts analytics; `setConsent(false)` stops it and discards any ongoing capture. `Blaze.disable()` also stops analytics and discards capture; its return is a promise for capture cancellation. Neither deletes already received events. The host owns consent and deletion workflows.
- `Blaze.track(name, properties?)` sends supported instrumented events only while consent is active. It returns no receipt. Unknown names are ignored. Do not call the internal `active_play` event directly.
- `visit` and `loaded` are sent automatically on activation; `exit` is attempted on page hide. Pointer-down samples are normalized viewport coordinates, rate-limited to at most one per second. They are not semantic actions or replay. On a new session after inactivity, `visit` and `loaded` are emitted again where applicable.
- Instrument `first_action` for the first meaningful gameplay action, `round_start` at round start, `round_complete` when a round ends, `retry` on a retry, `progression` on progress, and `error` for a stable error code. `first_action` is sent at most once per session. These names retain their existing funnel meaning; do not use them for unrelated UI clicks.
- For semantic detail, call `ui_click`, `player_action`, or `milestone` with `{key, value?}`. `key` is required, 1–40 ASCII letters, digits, `_` or `-`; `value`, if provided, is a finite number from 0 to 1,000,000. Use a fixed code defined by the developer, such as `start_button`, `move_left`, or `level_2`, not user-supplied content. Other properties are stripped. An invalid key or value drops the event both in the SDK and on the server. Arbitrary event names and custom property keys are not supported. These events do not replace the funnel events.
- Other events accept only `step`, `level`, `result`, `code`, `x`, `y`, `duration`, plus SDK-generated pointer `surface` and `screen`. Server storage retains finite numbers and strings matching 1–80 letters, digits, `_`, `.`, `:`, or `-`; unsupported keys and values are dropped. For pointer events, coordinates must be 0–1, and screen identifiers must be 1–40 letters, digits, `_`, or `-`. Use stable codes, not free text or personal data. The frame bridge has stricter per-event rules.

## Identity, delivery and activity

After consent, a pseudonymous player ID is kept in localStorage per SDK key, and a session ID and session state in sessionStorage per key. Storage failure can prevent identity persistence. A new session starts after 30 minutes without an event. IDs and timestamps are generated client-side; timestamps are ISO UTC and monotonically advanced within the loaded SDK. The server ignores events older than seven days or over one minute in the future. Do not send personal data in URL paths or campaign values: query and fragment are stripped from page/referrer, except `utm_source` and `utm_campaign` are separately sent (up to 100 characters).

Each event is sent immediately as a separate `keepalive` fetch to `/api/collect`, without cookies. There is no batch queue, public flush method, retry, or durable offline buffer. Browser shutdown and network errors can lose events. The server deduplicates event IDs within a game and event kind; this is not a guarantee that separately generated repeated actions are deduplicated. A request may return `accepted: 0` when all events were filtered or already received. Requests require a registered Origin and can be rate limited or temporarily paused.

A `round_start` begins active-play coverage with a zero-duration marker. While the game page is foreground and focused, trusted input extends an activity window by 15 seconds. The SDK periodically sends elapsed whole seconds, capped at 15 per increment, and stops on `round_complete`, `exit`, or page hide. The server caps positive increments to one per 15-second session bucket. Coverage indicates an instrumented round, not proof of continuous human play; missing markers mean duration is unknown rather than zero. Opaque frame activity requires the reviewed bridge. Studio-marked worker sessions suppress human telemetry, but this is not general bot detection.

## Frame, capture and automation boundaries

`Blaze.attachFrame` supports the separately reviewed v1 private MessagePort bridge for a trusted parent and a sandboxed game. It has a fixed lifecycle-event vocabulary, activity and pointer rules, and an optional gameplay-only image path; the new semantic event names above are **not** accepted through that bridge. Do not change a game's sandbox or send private data to make it work. Implement against the full [Frame v1 contract](./frame-v1.md), including fresh timestamped frame gates and preview restrictions.

Optional human canvas capture needs owner-reviewed configuration and separate affirmative recording consent. Use `Blaze.startCapture({consent:true})`, `Blaze.stopCapture()` to save, `Blaze.stopCapture({discard:true})` to discard, and `Blaze.getCaptureState()` or `blaze:capturestatus` to report status. It is sampled and may be unavailable; it records only a reviewed canvas copy with masks, no audio or DOM, and requires a persisted human visit. See the integration's capture documentation before enabling it.

The separate recording agent needs a game-specific `window.gameMarketingAdapter` with bounded `getState()`, `actions` and `act(id)` operations, or another explicitly supported strategy. SDK analytics alone does not create an adapter or make an arbitrary engine automatically playable. State and actions must exclude private data and account, purchase, messaging, or navigation operations.

## Optional human canvas recording

Recording is off unless the game owner enables it and reviews the capture surface. The owner must configure one unique canvas selector and up to eight normalized mask rectangles (`x`, `y`, `width`, `height` between 0 and 1). Configure masks around every private region that can appear inside the canvas. The SDK copies only that canvas, paints masks black and records the copy; page inputs, chat, other DOM and audio are excluded. Canvas content must be origin-clean. A canvas can itself contain sensitive information, so do not enable recording until its contents and masks have been reviewed.

Ask for **separate affirmative recording consent** after analytics consent. Analytics consent alone never starts recording. Call only from a human player’s explicit choice, never from the agent play adapter:

```js
const state = await Blaze.startCapture({ consent: true });
// Show state.status to the player (recording, not_sampled, quota_reached,
// unsupported, failed, or another documented state).
await Blaze.stopCapture(); // Stop and save.
await Blaze.stopCapture({ discard: true }); // Withdraw and discard.
// Blaze.disable() or setConsent(false) also discards the current capture.
```

`Blaze.getCaptureState()` and `blaze:capturestatus` events expose status, a stable failure reason where applicable, and a capture ID where available, never the grant token. Recording is sampled; a player can consent and still be `not_sampled` or encounter `quota_reached`. The server also requires a persisted human visit. Capture is capped at 5 frames per second, 960×540, 400 kbps, 30 seconds and 3 MiB. A supported WebM or MP4 MediaRecorder codec is required. Failures such as unsupported APIs, a tainted canvas, an invalid selector or upload failure are reported explicitly. Grant and upload requests omit cookies and are scoped to the configured game origin. Browser and network failures can prevent cancellation; tell users that application-level deletion remains available to the owner.

The fixture has separate tracking and recording controls and is intended only for controlled acceptance, not production player consent.

Uploads include the recorder's actual start timestamp so event seeking stays aligned when the recording-grant response is delayed. The server validates that timestamp against its bounded grant window. Older footage without this field uses approximate grant-time alignment, labeled in Sessions. Retention still starts at the server-issued grant time.

The studio worker reserves `window.__WEB_GAME_STUDIO_AGENT__ === true` for its automated game sessions. The worker injects an immutable marker before game code runs; when present, this SDK sends no human analytics, creates no analytics IDs in browser storage, and returns `agent_session` from `startCapture` without requesting a grant. This covers the studio's own automation; the marker is not general bot detection or a fraud-prevention boundary.

A recording stops and attempts to save as soon as its page becomes hidden, avoiding extended background recording when browsers throttle timers. An in-progress capture is discarded on page exit; an unload can interrupt that cancellation request, so the server expires unused grants. A page hidden before recording starts is cancelled.


## Game manifest and profile

Blaze identifies telemetry by the registered game's public SDK key. The Blaze game ID is an opaque dashboard record ID and is independent of a Forever manifest's `id` and `slug`; no game ID is accepted by `Blaze.init`. For example, WHOT's Forever manifest has id `last-card` and slug `whot`; neither is necessarily its Blaze game ID.

For a registered HTTPS game URL matching `/games/<slug>`, the profile reader tries `/games/<slug>/forever.json` on that same registered origin, without switching hosts. For example, `https://forever.138-68-247-33.sslip.io/games/whot` maps to `https://forever.138-68-247-33.sslip.io/games/whot/forever.json`. It requires a public-safe fetch, does not follow redirects, and requires format version 1 and a matching slug. It validates a bounded subset: `id`, `slug`, `name`, `genre`, `description`, `about`, `howToPlay`, `faq`, `controls.label` and `visibility`, and records source URL, observation time and SHA-256. This is not validation of the complete Forever manifest schema. Other URL shapes have no automatic mapping. The endpoint is planned and not yet implemented or deployed in the inspected Forever source; the profile reports unavailable, unsupported or invalid when applicable. A manifest does not provide consent, replace an SDK key, or make a game playable by an agent.
