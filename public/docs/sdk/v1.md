# Blaze browser SDK reference v1

Start with the [quickstart](https://blaze-bensigo.netlify.app/docs/sdk/quickstart.md). The SDK is a classic browser script, exposed as `window.Blaze`. `window.GameMarketing` is a deprecated alias. Load it from `https://blaze-bensigo.netlify.app/sdk.js`; `Blaze.init({endpoint, sdkKey, consent?, test?})` requires an HTTP(S) app origin and the game's public SDK key. The endpoint is reduced to its origin. Register the game's exact origin in Blaze. The game ID is for dashboard and API identification, not an `init` parameter. The key is public and identifies the game; never embed secret credentials. The game page must implement its own affirmative consent choice.

For a controlled test session, initialize with `test: true`. This boolean marks every SDK event in that session and uses a separate session ID; it does not grant consent or change synthetic-worker identity. The Most played games ranking excludes marked sessions. Other existing analytics may still include them; use an isolated test workspace when clean overall metrics are required. Omit the option or use `false` for actual audience sessions. Unmarked tests cannot be identified reliably, and public clients can set this flag themselves.

## Analytics API

- `Blaze.setConsent(true)` starts analytics; `setConsent(false)` stops it and discards any ongoing capture. `Blaze.disable()` also stops analytics and discards capture; its return is a promise for capture cancellation. Neither deletes already received events. The host owns consent and deletion workflows.
- `Blaze.track(name, properties?)` sends supported instrumented events only while consent is active. It returns no receipt. Unknown names are ignored. Do not call the internal `active_play` event directly.
- `visit` and `loaded` are sent automatically on activation; `exit` is attempted on page hide. Pointer-down samples are normalized viewport coordinates, rate-limited to at most one per second. They are not semantic actions or replay. On a new session after inactivity, `visit` and `loaded` are emitted again where applicable.
- Instrument `first_action` for the first meaningful gameplay action, `round_start` at round start, `round_complete` when a round ends, `retry` on a retry, `progression` on progress, and `error` for a stable error code. `first_action` is sent at most once per session. These names retain their existing funnel meaning; do not use them for unrelated UI clicks.
- For semantic detail, call `ui_click`, `player_action`, or `milestone` with `{key, value?}`. `key` is required, 1–40 ASCII letters, digits, `_` or `-`; `value`, if provided, is a finite number from 0 to 1,000,000. Use a fixed code defined by the developer, such as `start_button`, `move_left`, or `level_2`, not user-supplied content. Other properties are stripped. An invalid key or value drops the event both in the SDK and on the server. Arbitrary event names and custom property keys are not supported. These events do not replace the funnel events.
- Other events accept only `step`, `level`, `result`, `code`, `x`, `y`, `duration`, plus pointer `surface` and `screen`. Server storage retains finite numbers and strings matching 1–80 letters, digits, `_`, `.`, `:`, or `-`; unsupported keys and values are dropped. For pointer events, coordinates must be 0–1, and screen identifiers must be 1–40 letters, digits, `_`, or `-`. Use stable codes, not free text or personal data. The frame bridge has stricter per-event rules.

### Game-space pointers

The automatic `pointerdown` sample is normalized against the browser viewport and tagged `surface: "viewport", screen: "viewport"`. It is not a game-space heatmap. For an ordinary page, a developer may deliberately instrument a reviewed gameplay surface and send `Blaze.track("pointer", {x, y, surface: "game", screen: "level_1"})`, with `x` and `y` normalized to 0–1 relative to that surface and a stable screen code. Only do this for real gameplay input and exclude private regions; the SDK does not verify that those coordinates describe game space. Sandboxed frames use the stricter [Frame v1 contract](https://blaze-bensigo.netlify.app/docs/sdk/frame-v1.md). Neither sample is a gameplay replay.

For a reviewed surface with no private regions, replace `#game` and the screen code with your own stable values. This example deliberately limits its own samples to one per second:

```js
const surface = document.querySelector("#game");
let lastGamePointer = 0;
surface?.addEventListener("pointerdown", (event) => {
  const now = Date.now();
  if (!event.isTrusted || now - lastGamePointer < 1000) return;
  const box = surface.getBoundingClientRect();
  if (!box.width || !box.height) return;
  lastGamePointer = now;
  Blaze.track("pointer", {
    x: Math.max(0, Math.min(1, (event.clientX - box.left) / box.width)),
    y: Math.max(0, Math.min(1, (event.clientY - box.top) / box.height)),
    surface: "game",
    screen: "level_1"
  });
});
```

The automatic viewport sample and your game-space sample may both describe the same input. The dashboard keeps their coordinate spaces separate. Sample totals are not click totals.

## Identity, delivery and activity

After consent, a pseudonymous player ID is kept in localStorage per SDK key, and a session ID and session state in sessionStorage per key. Storage failure can prevent identity persistence. A new session starts after 30 minutes without an event. The SDK does not persist the host's consent decision; the host owns that choice and any permitted consent persistence. Withdrawal stops new collection but does not remove existing IDs or previously received events. IDs and timestamps are generated client-side; timestamps are ISO UTC and monotonically advanced within the loaded SDK. The server ignores events older than seven days or over one minute in the future. Do not send personal data in URL paths or campaign values: query and fragment are stripped from page/referrer, except `utm_source` and `utm_campaign` are separately sent (up to 100 characters). Values are not redacted; do not put personal data in campaign parameters.

Each event is sent immediately as a separate `keepalive` fetch to `/api/collect`, without cookies. There is no batch queue, public flush method, retry, or durable offline buffer. Browser shutdown and network errors can lose events. The server deduplicates event IDs within a game and human/agent kind; this is not a guarantee that separately generated repeated actions are deduplicated. A request may return `accepted: 0` when all events were filtered or already received. Requests require a registered Origin and can be rate limited or temporarily paused.

A `round_start` begins active-play coverage with a zero-duration marker. While the game page is foreground and focused, trusted input extends an activity window by 15 seconds. The SDK periodically sends elapsed whole seconds, capped at 15 per increment, and stops on `round_complete`, `exit`, or page hide. The server caps positive increments to one per 15-second session bucket. Coverage indicates an instrumented round, not proof of continuous human play; missing markers mean duration is unknown rather than zero. Opaque frame activity requires the reviewed bridge. Studio-marked worker sessions suppress human telemetry, but this is not general bot detection.

## Frame, capture and automation boundaries

`Blaze.attachFrame` supports the separately reviewed v1 private MessagePort bridge for a trusted parent and a sandboxed game. It has a fixed lifecycle-event vocabulary, activity and pointer rules, and an optional gameplay-only image path; the new semantic event names above are **not** accepted through that bridge. Do not change a game's sandbox or send private data to make it work. Implement against the full [Frame v1 contract](https://blaze-bensigo.netlify.app/docs/sdk/frame-v1.md), including fresh timestamped frame gates and preview restrictions.

Optional human canvas capture needs owner-reviewed configuration and separate affirmative recording consent. Use `Blaze.startCapture({consent:true})`, `Blaze.stopCapture()` to save, `Blaze.stopCapture({discard:true})` to discard, and `Blaze.getCaptureState()` or `blaze:capturestatus` to report status. It is sampled and may be unavailable; it records only a reviewed canvas copy with masks, no audio or DOM, and requires a persisted human visit. See the integration's capture documentation before enabling it.

The separate recording agent needs a game-specific `window.BlazeGameAdapter` (or legacy `window.gameMarketingAdapter`) with bounded `getState()`, `actions` and `act(id)` operations, or another explicitly supported strategy. SDK analytics alone does not create an adapter or make an arbitrary engine automatically playable. State and actions must exclude private data and account, purchase, messaging, or navigation operations.

## Optional human canvas recording

Recording is off unless the game owner enables it and reviews the capture surface. The owner must configure one unique canvas selector and up to eight normalized mask rectangles (`x`, `y`, `width`, `height` between 0 and 1). Configure masks around every private region that can appear inside the canvas. The SDK copies only that canvas, paints masks black and records the copy; page inputs, chat, other DOM and audio are excluded. Canvas content must be origin-clean. A canvas can itself contain sensitive information, so do not enable recording until its contents and masks have been reviewed.

Ask for **separate affirmative recording consent** after analytics consent. Analytics consent alone never starts recording. Call only from a human player’s explicit choice, never from the agent play adapter:

```js
const state = await Blaze.startCapture({ consent: true });
// Show state.status to the player (recording, not_sampled, quota_reached,
// unsupported, failed, or another documented state).
await Blaze.stopCapture(); // Stop and save.
await Blaze.stopCapture({ discard: true }); // Withdraw and discard.
// Blaze.disable() or setConsent(false) also discards the current capture.
```

`Blaze.getCaptureState()` and `blaze:capturestatus` events expose status, a stable failure reason where applicable, and a capture ID where available, never the grant token. Recording is sampled; a player can consent and still be `not_sampled` or encounter `quota_reached`. The server also requires a persisted human visit. Each capture segment is capped at 5 frames per second, 960×540, 400 kbps, 30 seconds and 3 MiB. The reviewed configuration may permit up to four segments. A supported WebM or MP4 MediaRecorder codec is required. Failures such as unsupported APIs, a tainted canvas, an invalid selector or upload failure are reported explicitly. Grant and upload requests omit cookies and are scoped to the configured game origin. Browser and network failures can prevent cancellation; tell users that application-level deletion remains available to the owner.

Uploads include the recorder's actual start timestamp so event seeking stays aligned when the recording-grant response is delayed. The server validates that timestamp against its bounded grant window. Older footage without this field uses approximate grant-time alignment, labeled in Sessions. Retention still starts at the server-issued grant time.

Automation integrations can reserve `window.__WEB_GAME_STUDIO_AGENT__ === true` for its automated game sessions. A controlled browser runner can inject an immutable marker before game code runs; when present, this SDK sends no human analytics, creates no analytics IDs in browser storage, and returns `agent_session` from `startCapture` without requesting a grant. This suppresses explicitly marked automation; the marker is not general bot detection or a fraud-prevention boundary.

A recording stops and attempts to save as soon as its page becomes hidden, avoiding extended background recording when browsers throttle timers. On page exit the SDK attempts to stop and save an active or uploading capture; it cancels a capture that is still starting. Unload can interrupt either request, and unused grants expire. A page hidden before recording starts is cancelled.


## Game manifest and profile

Blaze identifies telemetry by the registered game's public SDK key. The Blaze game ID is an opaque workspace record and is separate from any game-owned manifest identity. `Blaze.init` uses the public SDK key, not a game ID.

Add any publicly accessible HTTP(S) game-page URL. Blaze safely imports its title, available description and Open Graph artwork, with dated source provenance. Missing description/artwork stays missing rather than invented. A compatible version-1 manifest at `<game-url>/forever.json` is optional and takes precedence when valid; the legacy filename remains supported for installed integrations. Public-address checks, standard ports, request/body limits and no redirects apply to both paths. Private URLs cannot be imported.

Metadata import does not collect analytics or prove a game is playable. Install and verify the SDK, consent controls and optional frame/capture integration separately. Owner edits remain separate from source facts.

### Optional same-site identity scope and player profile

`Blaze.init({endpoint, sdkKey, consent:false, identityScope:'your-platform'})` opts an integration into one consented browser ID across its games on the same site. The default remains a separate ID per game. This does not identify a person or join devices or websites. Existing game-specific IDs cannot be joined retroactively. The host must disclose this scope and remove `gm_player_*` and `gm_session_*` storage entries on withdrawal, including when no game is active.

`Blaze.track('player_profile', {age_band:'25-34', declared_country:'NG', interests:'sports,puzzle'})` sends explicitly volunteered answers only. Age bands are `18-24`, `25-34`, `35-44`, `45-54`, `55-plus` or `unknown`; country is an uppercase two-letter self-reported code or `unknown`; interests are comma-separated `action`, `sports`, `cards`, `puzzle`, `rhythm`, `trivia`, `party`, or `unknown`. Do not infer these answers from gameplay. Sending `unknown` clears that answer from the latest-profile aggregate, not historical events. All fields remain optional to the player. Trusted network country is measured separately.

Failed ingestion requests dispatch `blaze:deliverystatus` with `{status:'failed', httpStatus}`; `0` indicates a network failure. The event contains no response body or private URL. A host may report a fixed failure code to its own operational diagnostics. Delivery remains best effort; ad blocking, offline exits and browser shutdown can leave gaps.
