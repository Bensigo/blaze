# Recording worker

The worker runs separately from the web server and polls for leased jobs. Real games require the isolated deployment in `compose.worker.yml`: a worker, a per-job egress guard, and a browser on an internal-only network. Put `APP_URL`, `WORKER_TOKEN`, and a unique random `EGRESS_TOKEN` of at least 32 characters in a private env file outside the repository, then run `docker compose --env-file /path/to/private.env -f compose.worker.yml up -d --build` on the chosen worker host. For Neon private S3, configure only the web server with `NEON_STORAGE_ENDPOINT`, `NEON_STORAGE_REGION`, `NEON_STORAGE_ACCESS_KEY_ID`, `NEON_STORAGE_SECRET_ACCESS_KEY` and `NEON_STORAGE_BUCKET`, then set `NEON_CLIENT_UPLOAD=true` on the worker. The worker receives a five-minute object-specific staging PUT capability, uploads outside the web function, and requests finalization. The server copies to a private final key before checking exact size/type and bounded media magic, then registers it under the active job. Cleanup pointers and deletion tombstones protect recovery; a presigned upload has no verified provider-enforced size cap. Authenticated reads redirect to a signed private GET for at most 60 seconds, so already issued read capabilities can outlive withdrawal by that much. No storage or administrative credentials enter game pages or the worker. Preserve the private Blob token for historical Blob records. For an existing Vercel Blob deployment, `BLOB_CLIENT_UPLOAD=true` remains supported; production worker multipart fallback is blocked. Local development supports multipart uploads. Use HTTPS for a remote app. Keep these tokens and the owner's Jev key out of game pages, logs and source control. The server supplies the encrypted-at-rest Jev credential only in an authenticated claim. With no key, a Jev recording fails explicitly. The worker calls [OpenRouter's System One API](https://openrouter.ai/docs/guides/community/typesafe-sdk) using the selected OpenRouter Jev credential and a pinned Jev 1.13 or 1.14 model. The server checks the queued settings and credential revisions before handing a claim to the authenticated worker. Provider metadata and mocked decisions do not establish credits or live Jev behavior.

The Compose network uses the fixed subnet `172.28.22.0/24`; choose a host without an overlapping network. No service ports are published. The browser container installs IPv4 and IPv6 firewall rules before dropping all capabilities and starting the browser manager as an unprivileged user. Its only permitted outbound connection is TCP to the guard proxy, and replies to worker-initiated control connections are allowed. The guard independently resolves every authorized destination, rejects non-public addresses or mismatches with the worker's pin, permits only per-job CONNECT authorities, connects directly to the verified public IPv4, expires the policy after three minutes, and closes active tunnels when a job ends. Worker and guard DNS answers that differ cause the run to fail closed. Chromium also receives hostname pins; UDP and QUIC are disabled. Per-job browser-control and guard requests use `EGRESS_TOKEN`; it is removed from the Chromium process environment.

The browser host image and firewall deployment require Docker and a kernel supporting the iptables rules. The Compose configuration has been parsed, and same-host remote Playwright, the guard proxy, real HTTPS/WSS and video transfer have been tested; the container topology, firewall and cross-container execution have **not** been run on a Docker host yet. Do not treat this as deployed or firewall-validated until that acceptance passes on the actual worker host. Arbitrary game runs fail if the isolated guard and browser cannot be reached and authenticated; the explicitly enabled local controlled fixture is the only local-browser exception.

The game must provide the adapter described in the public developer documentation (`/developers` and `/developers.md`). Actions and state must be safe to share with the configured model. The worker defaults to at most 30 actions and a 30-second gameplay decision window. A queued run can lower either limit to a whole number from 1 to 30; its limits are pinned at enqueue, checked on claim and checked by the worker. It also uses request and adapter timeouts, a lease heartbeat, real Playwright video and screenshots, and authenticated uploads. External keys never enter the browser page.

Per game, `resourceOrigins` allows additional exact HTTPS origins and `webSocketOrigins` allows exact WSS origins. The game’s own HTTPS origin is included for resources by default; even a same-host WSS connection requires explicit permission. Entries are origins only, with no credentials, path, query, fragment or wildcard. The server validates each host when saved, and the worker re-resolves each host at run time, rejects private or reserved IPv4 answers, and pins an approved public IPv4 in Chromium. HTTPS certificate verification remains enabled. Chromium request interception checks each redirect hop; sockets are routed before game navigation. Service workers, downloads, frame navigations and dedicated/shared workers are blocked. The worker adds a restrictive document policy and caps buffered document data at 8 MiB to apply it; games that require frames or browser workers will not run under this policy. The controlled fixture never gains extra origins from game settings.

The firewall is essential: Playwright interception, the document policy, and JavaScript API restrictions alone are not an egress boundary. The browser sets an immutable `__WEB_GAME_STUDIO_AGENT__` marker before page creation, and blocks requests and redirects to the app's `/api/collect` and `/api/capture` paths so synthetic traffic does not become human SDK telemetry. Authenticated worker telemetry is sent by the separate worker process. The game page executes third-party code, so record only games you trust.

`tests/network-policy.test.ts`, `tests/network-egress.test.ts`, and `tests/network-remote.test.ts` use real Chromium, a real proxy, separate TLS origins, a real WebSocket handshake and a saved remote-browser video. Its self-signed certificates, loopback transport remapping and disabled local-network checks exist only in the test; production does not enable them. The fixture does not prove live production connectivity or validate Jev.

For local acceptance only, install dependencies and Playwright Chromium, run `npm run worker` with `APP_URL`, `WORKER_TOKEN` and `ALLOW_LOCAL_FIXTURE=true`, and add the exact URL `http://127.0.0.1:3000/fixture/index.html` as a game. Fixture mode only permits this app’s controlled fixture at `/fixture/index.html` (including its public HTTPS deployment), uses deterministic moves, and is labeled as such. It does not validate Jev. The fixture can also be played with buttons, arrow keys and Enter. Synthetic events use the authenticated worker route; ordinary SDK calls remain human traffic.

Clips are generated by ffmpeg from the actual recording, with aspect-preserving letterbox/pillarbox for landscape, portrait and square. Source and output are temporary files removed after each job; assets must be stored by the server in persistent storage. The worker does not publish social posts. A running worker, configured persistent asset storage, and a reachable authorized game are operational dependencies; serverless deployment alone does not run browser jobs.

Recording observations contain timestamped adapter phase changes, action and model-decision counts, the last observed phase, and whether completion was observed. Only a small vocabulary of phase and error names is retained; other values become unclassified rather than being copied from game state. A repeated unchanged state is a hypothesis to review, not a diagnosis. Page errors use bounded error categories and stable telemetry codes; messages, URLs, input text and credentials are excluded. Blocked external requests and WebSockets are reported as worker coverage limits, not game errors. A final-frame observation is timestamped when its screenshot was captured. On failure the worker attempts to save observations while its lease remains valid.

## Free-host compatibility status

Neon private S3 data-plane acceptance passed for a new private Blaze bucket: actual signed PUT, server-only COPY, exact HEAD metadata, anonymous read denial, signed Range bytes, full readback hash and download filename. This provider probe does not establish the web authorization route, hosted video playback or worker integration; those require separate acceptance. Only the probe's newly created test objects were deleted, and Neon's physical retention after DeleteObject is not established. Runtime S3 credentials were recovered from the existing branch storage credential rather than creating another credential; the project administrative key is operator-local only.

Cloudflare Browser Run is not currently an interchangeable runtime for the non-fixture worker. The current worker uses the Playwright server protocol behind the container firewall, and Browser Run documents incomplete video support. No public CDP relay or application interception can replace the existing network boundary. A Browser Run primitive probe must stay separate from actual application-worker acceptance.

Netlify reserves AWS_REGION and other AWS runtime names. Use the NEON_STORAGE_* settings above on that host; they take precedence over platform credentials and partial custom configuration fails closed. The explicit AWS_* configuration remains supported when no custom connection setting is present, for Neon-provided/local environments. Netlify Free Legacy does not allow per-function environment scopes; use private project configuration without NEXT_PUBLIC secrets. The administrative NEON_API_KEY is never a runtime setting.

## Decision evidence and a later real run

Paid Jev jobs are currently blocked unconditionally in direct/manual/scheduled enqueue and existing queued claims before credentials are returned. No environment flag bypasses this guard. The limits below describe prepared worker behavior, not permission to run it. An approved, enforceable total spending cap must be implemented and verified first; see [Actions readiness](ACTIONS.md). Completion commits recording evidence, Findings, job state and gate release atomically after ownership, media-kind and active-lease validation.

Current workers advertise `jev-actions-v1` on authenticated claim and heartbeat requests. The server skips limited jobs for missing or unrecognized protocol before sending any Jev credential; a fresh heartbeat alone is not sufficient. Heartbeat metadata contains only the recognized protocol and bounded-recording capability, never credentials. The per-claim check is authoritative if legacy and current workers coexist. This protocol is an authenticated capability declaration, not protection against a malicious holder of the worker token. Default-limit legacy runs and clips remain compatible. Upgrade/restart the worker and observe a fresh capable heartbeat before a limited test.

The worker keeps bounded traces of a selected allowed action, the safe adapter phase before it, and the next observed safe phase (or an explicit unobserved/failure outcome). It does not retain raw state or model responses. An adapter phase change is an observation, not proof of an intended outcome. The worker completion path can persist these as same-game Findings for owner review; fixture findings are labelled and never establish live Jev or human enjoyment. Reproduction needs the exact game/build, steps and recorded timestamp, with logs or screenshots when available. A single error or agent stall is not a confirmed bug.

A later separately approved smallest paid test should use a deliberately controlled, authorized game with two safe choices, a single pinned Jev decision, a strict spending cap, a running isolated worker, and a capture showing the next adapter state; stop after the first decision. Queue with `maxActions: 1` and `maxDurationSeconds: 30` to permit at most one model decision and one action; a forced first action may produce no model decision. The worker reads a final state if time remains. This is a gameplay decision window, not a total job deadline: navigation, in-flight operation cleanup, capture processing and upload can take longer. The cap limits calls, not input tokens, credits or dollar spend; a provider-side spending limit remains necessary. Record provider usage/cost and an explicit failure if the decision, action, next state or capture is missing. Do not use Forever until its owner authorizes the live integration.
