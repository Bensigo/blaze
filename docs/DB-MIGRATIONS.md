# Database migrations

Production uses a PostgreSQL database supplied through `DATABASE_URL`. Before deploying a release, set the connection in the shell or deployment environment and run `npm run db:migrate`; do not put connection strings or credentials in logs. The command uses one checked-out connection, a transaction-scoped advisory lock, and versioned migrations. A failed migration rolls back and can be retried. Runtime requests check the applied schema version and do not run DDL.

The current schema version is 4. Migration 2 creates `player_first_seen` and installs an `AFTER INSERT` statement trigger before backfilling existing human events. Trigger installation locks the events table during migration, so existing and new writers maintain first-seen records once it commits. It does not remove telemetry. First-seen ties use timestamp then session ID; duplicate event IDs cannot move first-seen. Migration 3 restricts the application tables to server access. Migration 4 adds a bounded capture segment index and per-session segment uniqueness; legacy writers keep segment 0. It does not remove existing capture grants or footage.

Local PGlite development and tests apply migrations automatically. Normal PostgreSQL requests have a 15-second statement timeout; migrations use a 120-second statement timeout and a 10-second lock timeout. Longer backfills may need an operational migration plan, and a lock timeout or failure leaves the prior schema intact. Confirm migration success and database permissions on the target environment before routing the new release to it. Raw event retention is not configured by this migration.

Set `DATABASE_STORAGE_LIMIT_BYTES=1073741824` for the intended free-plan guard and recheck the actual plan and unit before production configuration. When configured for PostgreSQL, the app caches `pg_database_size(current_database())` for 30 seconds and rejects both human and synthetic event ingestion at 80% of the configured limit; failed or invalid measurements also pause ingestion. PGlite skips this check. The measurement covers only the current database: Neon project, branch and history accounting can differ, and a 30-second cache allows additional writes before the next check. This is an admission estimate, not a hard storage cap or a throughput guarantee. Workspace, authentication, and control writes are not subject to this event-ingestion gate, but can still fail if the actual provider quota is reached. No event retention or deletion is configured; set and approve a retention policy separately.
